**Important consequence:** module scripts (`type="module"`) are always deferred — they run after
the entire document is parsed, *regardless* of where they sit in the source. Classic `<script>`
tags run synchronously, immediately, in document order. That means blocks 7, 8, 9 — which appear
*after* the module block in the file — actually **execute before it at runtime**. The current code
already tolerates this (everything that touches `window._rtX` / `window.auth` / `window.db` does so
defensively, e.g. `if(window._rtQuery && ...)`, and only from inside functions called later, never
at top-level/import time). If the refactor changes more scripts to `type="module"`, this timing
relationship must be re-verified, not assumed — converting a currently-classic block to a module
changes when it runs relative to everything else. **Recommendation: keep every currently-classic
script classic in the rebuilt `index.html`; only the one already-module block stays a module**,
unless you want to invest in re-verifying timing for a full ESM conversion.

  These don't collide today (one's a bare global, one's `RBAC.getVisibleProjects`), but when

  pattern (it snapshots whatever `_xlGetData` is *at that point in the file*, top to bottom). Any
  reordering during extraction must keep `_xlGetData`'s declaration before this line, or the
  snapshot silently becomes `null`. Flagging per your "don't fix, just note" instruction — not
  proposing a change here, just marking it as an ordering trap for step 3.
- One `onkeydown` handler (line 1827, login password field, `Enter` → `handleLogin()`) is the only
  non-mouse/non-form handler in the whole file — easy to miss if scanning is narrowed to
  click/change/input only.
